# InteRun — Design Brief (for design collaborators, incl. ChatGPT)

This document lets a design collaborator (e.g. ChatGPT) propose look-and-feel changes for
**InteRun** that drop straight into the codebase without breaking it. **Claude keeps overall
control of the project**: a collaborator proposes CSS / layout / visual direction, and Claude
integrates it, builds, tests, and ships. Please read this whole file before proposing changes.

---

## 1. What you're looking at

InteRun is **"The Intelligent Training Companion"** — an evidence-based running-coach PWA
(mobile web app). It builds a personalised training plan, runs live GPS sessions with voice
coaching, logs runs, and shares a branded run card.

**See it live:** https://padder1980.github.io/Inte-Run/
The entire app is a single self-contained page — do **View Source** on that URL and you get all
the HTML, CSS, and JavaScript in one file. That's the whole design surface.

**Source repo:** https://github.com/Padder1980/Inte-Run (public)

### The one architectural fact you must know

This is **not** a normal multi-file website. There are **no separate page files.** Everything is
generated by one TypeScript build script, `web/app.ts`, which emits the self-contained
`web/app.html` (and the deployed `docs/index.html`). Inside `web/app.ts`:

| Region | Lines (approx.) | What it is |
|---|---|---|
| Brand mark (logo SVG) | ~16–40 | The InteRun logo, as inline SVG |
| **`<style>` block** | **~41–635** | **All CSS lives here. This is where 95% of design work happens.** |
| HTML shell | ~636–668 | Splash, welcome screen, top bar, `<main>`, bottom nav |
| Runtime JS | ~669–2900 | The app logic + every screen's markup, built as strings |

Each **screen** is rendered by a `viewX()` function that returns an HTML string using CSS classes
from the `<style>` block. So "restyle the Plan page" almost always means **edit CSS rules**, and
occasionally **adjust the class names / structure** inside a `viewX()` function.

## 2. How to hand work back (please follow this)

Because Claude integrates everything, give changes in whichever of these forms fits:

1. **CSS edits** (preferred). Target the existing class names. Give the full rule(s) you want,
   e.g. "change `.cal-week` to …". New components: propose new class names + their CSS.
2. **A described visual direction** ("make the run overview feel more like a premium fitness
   dashboard: bigger hero number, card elevation, …") with reference images if you have them.
3. **Small HTML structure tweaks** — describe them against the named `viewX()` function and the
   classes involved; Claude will wire them in.

**Please do NOT:**
- Rewrite `web/app.ts` wholesale, or hand back a full new file.
- Touch the runtime **JavaScript logic** (state, GPS, plan generation) — that's Claude's domain.
- Introduce external assets: **no external CSS/JS/font/image URLs.** The app is offline-capable
  and self-contained; everything must be inline. System fonts only (see tokens). SVG/emoji for
  icons. (Map tiles are the *only* network asset and are already handled.)
- Use CSS `@import`, or anything that assumes a build tool / framework. Plain CSS only.

Every change **must work in both light and dark themes** (see §3) and stay **mobile-first** — the
app renders in a `440px` max-width column (`.app`), so design for a phone.

## 3. Design tokens (use these — don't hard-code colours)

All colour comes from CSS custom properties defined three times: a light default, a
`prefers-color-scheme: dark` block, and explicit `:root[data-theme="light"|"dark"]` overrides for
the in-app theme toggle. **If you add or change a colour, set it as (or from) a token, and provide
both light and dark values.** Use `color-mix(in srgb, var(--accent) N%, …)` for tints (the
codebase does this heavily) so tints track the theme automatically.

| Token | Light | Dark | Role |
|---|---|---|---|
| `--bg` | `#eef1f1` | `#0a100e` | App background |
| `--surface` | `#ffffff` | `#151e1b` | Cards / sheets |
| `--surface-2` | `#f6f8f8` | `#1b2622` | Insets, secondary fills |
| `--line` | `#dbe1e0` | `#26332e` | Borders / dividers |
| `--ink` | `#14201b` | `#e7eeea` | Primary text |
| `--ink-soft` | `#4c5b55` | `#a9b7b0` | Secondary text |
| `--ink-faint` | `#7a877f` | `#74847c` | Labels, captions |
| **`--accent`** | **`#0e8c7f`** | **`#2bb3a3`** | **Brand green — primary actions, highlights** |
| `--accent-ink` | `#ffffff` | `#06231f` | Text/icon on an accent fill |
| `--shadow` | soft 2-layer | deeper 2-layer | Card elevation (use `box-shadow: var(--shadow)`) |

**Phase / intensity accents** (used by the plan + calendar; keep their meaning):
`--base` (aerobic, teal-blue) · `--build` (green) · `--peak` (orange) · `--taper` (violet).
Effort tints: `--eff-easy` · `--eff-moderate` · `--eff-hard` · `--eff-none`.

**Brighter "signal" greens** (used only on the route line / share card, on dark map imagery):
`#17c98f`, `#3dffb0`, `#a7ffd8`. Don't use these for UI chrome — `--accent` is the UI green.

### Type
- `--sans`: system UI stack (`system-ui, -apple-system, "Segoe UI", Roboto, …`).
- `--brass` / `--brass-tint`: the warm complement of the accent, used ONLY on the profile screen and
  ONLY for section furniture — the numbered badge, the rule under a section heading, and the card's
  top edge.
  ⚠️ **Brass marks STRUCTURE; teal marks ACTION.** The profile is the longest screen in the app and
  every section looked identical, so there was nothing to navigate by while scrolling. The rule that
  makes a second colour safe here is that it never touches anything you can press: colour the
  chapter headings, not the sentences. Tinting whole sections, or giving each section its own
  colour, turns a long form into a rainbow and destroys the one signal that matters — what is a
  heading and what is a control. Do not extend brass to buttons, links or inputs, and do not use it
  outside `#view:has(#saveProfile)`.
  `--brass-sheen` / `--brass-shade` give it the metallic finish: the piping fades to nothing at both
  ends rather than mitring into a hard corner (a pseudo-element, not a border — a border cannot
  fade), and carries an off-centre specular highlight, which is what makes metal read as metal
  rather than as a blurred line.
  ⚠️ **The sheen is neutral light and shade, per theme — never a mix toward `--brass`.** Brass is the
  DARK colour in light mode and the LIGHT colour in dark mode, so a single gradient written in terms
  of it darkens the face in one theme and lightens it in the other, and either way it eats the
  contrast of the digit sitting on it. Measured when it was written that way: 4.66 → 4.11 light and
  7.48 → 3.72 dark, both under the bar. White is dialled right down in dark, because a bright
  highlight under light text is exactly what costs contrast there.
  Contrast is measured, not eyeballed, and measured on the band the digit actually occupies: 4.50:1
  light and 6.63:1 dark. Keep it above 4.5 if any of these values move.
- `--fig`: the numeral stack — used via `.num` for **all numbers/stats** with
  `font-variant-numeric: tabular-nums`.
  ⚠️ **It is the SAME sans as body text, not a monospace stack** (owner's call, 2026-08-02, comparing
  against a reference app he sent). It used to be `--mono` (SF Mono et al) and that was wrong: a code
  font in a running app reads as a spreadsheet, and the wide digits made every stat look spaced out —
  "6.44 km" sat with gaps between the characters. Tabular figures are kept, because not jittering as
  a clock ticks or a splits column updates was the only thing the mono stack was genuinely buying;
  the 12 other selectors that had leaned on the monospace for their alignment now ask for tabular
  figures explicitly. Don't reinstate a monospace here.
- Rough scale in use: captions ~10.5–12.5px, body ~13.5–14px, titles ~17–21px, hero numbers 24px+.

### Shape & spacing
- Radii: chips/inputs ~7–11px, cards ~14–16px, sheets/large panels ~22px. Pills use `999px`.
- Cards: `background: var(--surface); border: 1px solid var(--line); border-radius: 16px;
  box-shadow: var(--shadow);` — that's the house card. Stay consistent with it.
- Padding rhythm is multiples of ~2px around a 14–16px base; content gutter is ~16px.

### Brand signatures (keep these recognisable)
- **Marching-ants line:** the animated flowing dashed line — brand accent under white dashes —
  used on the "Start session" button outline (`.start-btn::before`) and the route on the run
  overview. It's a core motif; enhance it, don't remove it.
- **Premium-but-calm** tone: generous whitespace, soft elevation, one confident green accent,
  restrained motion. Evidence-based coaching = trustworthy, not gamified/loud.

## 4. Screen inventory (what to point your design at)

Each lives in a `viewX()` function in `web/app.ts`; the CSS classes it uses are in the `<style>`
block. The main ones you mentioned are marked ★.

| Screen | Function | Notes |
|---|---|---|
| ★ **Today** | `viewToday` | Home: today's session, start button, weather/conditions, welcome-back |
| ★ **Plan** | `viewPlan` | The multi-week training plan overview (phases: base/build/peak/taper) |
| Calendar | `viewCalendar` | Week-by-week calendar (`.cal-*` classes) |
| ★ **Activities** | `viewActivities` | Logged runs list + empty state (`.runcard`, `.empty-acts`) |
| ★ **Run overview / detail** | `viewRunDetail`, `viewLiveComplete` | Post-run summary: real map + route, stats, splits, share (`.ov-*`, `.sp-*`) |
| ★ **Setup / onboarding** | `viewSetup` | Profile & goal wizard (`.q`, `.sel`, section cards) |
| ★ **Share card** | `buildShareCanvasCore` | The shareable PNG — **canvas-drawn**, dark "dashboard" style. Not CSS; described separately if you want to touch it. |
| Live session | `viewLive` | In-run screen: current/avg/lap pace, live GPS |
| Performance | `viewPerformance` | Trends / bests |
| Community | `viewCommunity` | |
| Support | `viewSupport` | Help hub incl. "Understanding my sessions" |
| Session guide | `openSessionGuide` | First-run walkthrough of the numbers in a session title (`.guide-*`) |
| Session detail sheet | bottom sheet | `.sheet`, `.sd-*` — tap a session to see its breakdown |

> The **share card** is drawn on an HTML canvas (not styled with CSS), and it's deliberately a
> dark "premium dashboard" look. If you want to restyle it, describe the direction in words /
> reference images and Claude will translate it into canvas drawing — don't send CSS for it.

## 5. A good hand-back looks like this

> "On the Plan page, make each week feel like a distinct card and let the phase colour lead.
> Change `.cal-week` to a stronger elevation and a 3px left border in the phase colour:
> ```css
> .cal-week { border-radius: 18px; box-shadow: 0 2px 4px rgba(20,32,27,.05), 0 12px 30px -12px rgba(20,32,27,.12); border-left: 3px solid var(--phase, var(--accent)); }
> ```
> Set `--phase` per week to `--base`/`--build`/`--peak`/`--taper`. Keep dark mode readable —
> the tint should come from the token, not a hard-coded colour."

That's perfect: it targets a real class, uses tokens, respects both themes, and leaves the
integration + testing to Claude.

## 6. Workflow recap

1. You (the owner) point ChatGPT at this file + the live URL and say which screen to work on.
2. ChatGPT proposes CSS / a visual direction per §2.
3. You paste that back to Claude here.
4. Claude integrates it into `web/app.ts`, runs the build + typecheck + tests, screenshots the
   result in light and dark, and pushes to `main` (which redeploys the live site).

Nothing reaches the live app except through Claude — so the design can evolve freely while the
build stays green and the experience stays coherent.
